# Apply a Rune Brand

Carry one approved Rune into a product without turning the downstream repository into a second brand source of truth.

## Resolve the identity

Read the target repository instructions, current product surfaces, and existing asset conventions before proposing changes. Locate the canonical Runes repository and read `brand/runes.json`, `brand/tokens.json`, `brand/theme.css`, `docs/BRAND.md`, and `docs/PLATFORMS.md`.

Confirm that the target project has an entry in `brand/runes.json`. If it does not, use `$add-rune`; do not invent a local mark, color, tagline, or rationale inside the target repository.

Use assets only after `pnpm assets:check` passes in the Runes repository. When consuming a published archive instead, verify its SHA-256 against `public/downloads/manifest.json`. Report the Runes commit or manifest version used.

## Audit real surfaces

Inventory only surfaces the target actually owns. Map each proposed change to:

- the product surface;
- the canonical generated source;
- the target path or external setting;
- the light, dark, small-size, or mask treatment;
- the target repository verifier.

Read [references/surfaces.md](references/surfaces.md) for the artifact selection matrix. Do not import every platform pack by default. A CLI library may need a README lockup and GitHub social image but no favicon, app icon, or menu-bar asset.

If the request is broad and the surface choices would materially change the product, show the compact surface map before mutation. User-visible copy, layout taste, and external profile changes remain owner decisions.

## Integrate canonical outputs

Vendor the smallest useful set of generated assets into the target repository. Preserve the generated bytes and filenames where platform conventions allow it. Keep them under the repository's existing asset directory or a clear `runes/<slug>/` namespace.

Never:

- redraw the grid in Figma or another editor;
- edit generated SVG paths, colors, raster dimensions, ICO, or ICNS files;
- hotlink production UI to a mutable Runes development URL;
- distort, rotate, round, outline, shadow, or pre-mask the canonical mark;
- replace an established product design system when only a brand surface is requested;
- use the project accent as the only carrier of status or meaning.

Use `logo/horizontal.svg` where the project name must be read and its Paper or white field is controlled. Use a field-backed asset on uncontrolled light-and-dark surfaces. Select `logo/mark.svg` or `logo/mark-inverse.svg` for monochrome contexts, and reserve `logo/mark-duotone.svg` for a larger mark on a controlled light field. Repeated decorative marks use empty alternative text; the primary identity uses the project name.

For a frontend, integrate `brand/theme.css` through the existing token layer instead of copying isolated hex values throughout the codebase. Set `--runes-field` to the identity's accent token and use Acid as the signal color, except an Acid field uses Blue as its signal. Preserve the product's semantic success, warning, error, focus, and accessibility colors.

## Verify the applied brand

Compare every vendored asset hash with its canonical source. Render the exact changed surfaces, not just the raw files. Use `browser-cdp` for web, documentation, and browser-preview work, and inspect native assets in their target runtime when available.

Verify:

- the mark remains legible at the smallest real size;
- light and dark contexts select the correct mono variant;
- circular, app, and operating-system masks do not clip the Rune;
- surrounding text and controls meet the target product's accessibility contract;
- no layout shift, broken image, stale asset path, or unintended full-product reskin was introduced;
- the target repository's canonical gate passes.

External writes such as changing a GitHub social preview, X profile, app-store listing, or deployed site require explicit authorization. Prepare the exact asset and report the pending external action when that authorization is absent.

For refreshes, replace only files proven to be prior Runes outputs and preserve unrelated brand work. Report the surface-to-asset mapping, visual evidence, source revision, verification results, and anything not rendered. Do not commit, push, deploy, publish, or change canonical Rune geometry without explicit authorization.
